# GitHub walkthrough

Replace the bracketed fields in the prompts below. Use the same Issue and PR links when handing work to a new session.

1. **Create the project.** Choose **Use this template → Create a new repository** if available, or copy the repository files into a new repository. Follow [GitHub setup](github-setup.md), replace the starter architecture and roadmap, and verify the [Lean starter](../lean/README.md) if using Lean.
2. **Explore the mathematics.** Work with a planning assistant before commissioning individual investigations.

   > Read METHODOLOGY.md and AGENTS.md. Explore [mathematical objective], candidate definitions, library results and dependencies. Develop the architecture and roadmap with me and flag decisions that need my mathematical judgement.

3. **Plan and approve the commission.** As researcher, supply the informal claim and sources, review the draft, and resolve open mathematical choices. Use **Issues → New issue** if posting it yourself. Select **Formalisation task** for a bounded result, **Mathematical investigation** for an open question, or **Project review** for a milestone assessment.

   > Read the methodology and [prior Issue URLs]. Draft an Issue for [objective and sources] with semantic acceptance criteria, allowed scope, verification and a stopping rule. Show me the draft. After I approve the text and authorise posting, post it in [repository] and return its URL.

4. **Commission implementation.** Give the approved Issue URL to the implementation agent. Record substantive clarifications in the Issue discussion so they reach the next session.

   > Implement [approved Issue URL]. Read AGENTS.md, the Issue discussion and linked prior reports first. Follow the agreed scope and stopping rule. Open a linked PR if there is useful work to review and post a completion report on the Issue.

5. **Review and revise.** Open **Files changed** to compare the statement with the Issue and informal source, and **Checks** to inspect verification. Use **Review changes** to submit findings. After the implementer replies, have the reviewer recheck revisions. Repeat as needed. Merge only after required checks pass and the researcher accepts the result.

   > Independently review [PR URL and commit] against [Issue URL and informal source] using the reviewer guide. Post findings in the PR review with locations and evidence.

   > Address the review requests in [PR discussion URL] within the scope of [Issue URL]. Reply to each finding with the change and verification evidence or the reason it remains open. Record any substantive revision to the commission on the Issue.

6. **Record the outcome.** Use the [completion report](completion-report.md) as soon as the investigation stops or is handed over for review. Include failures and interruptions, even without a PR. For the next session, share the Issue and any active PR URLs.

If an assistant cannot read GitHub, share relevant excerpts that the project's confidentiality rules permit. If it cannot post, have it return the finished Issue, PR description, review, reply or completion report with its intended destination, then paste it there yourself.
